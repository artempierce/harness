01The one idea

The model remembers nothing. Working memory is rebuilt from storage on every single turn, then thrown away.

Everything else — three memory stores, a retrieval gate, a router, consolidation — exists to answer one question well: given this message, what should be in the context window this time?

An LLM call is stateless. It sees a system prompt and a message list, and nothing else. “The agent remembers I'm a QA engineer” is never true of the model. It is true of the assembly step that put that fact into the prompt before the call.

03Memory: four kinds, three stores

The names come from cognitive science and are worth keeping straight, because each has a different lifetime and a different failure mode.

Semantic memory uses keyword search, not embeddings

The facts table is an FTS5 virtual table — the index is the storage, so there are no triggers to keep in sync. Porter stemming means “deployment” matches “deploy”.

CREATE VIRTUAL TABLE facts USING fts5(
    content,
    source UNINDEXED, trace_id UNINDEXED, created_at UNINDEXED,
    tokenize = 'porter unicode61'
);

This is deliberate, it matches the reference architecture, and there is measured evidence for it — see §11.

04The retrieval gate

Most turns need no facts at all. Retrieving anyway costs tokens and pushes irrelevant context at the model, which makes answers worse, not merely slower.

if count() == 0:  return False, "nothing remembered yet", []
hits = search(text)
if not hits:      return False, "no fact matched", []
return True, f"{len(hits)} fact(s) matched", hits

The search runs before the decision. With a local index that costs microseconds, so what the gate protects is context, not latency. Backed by a vector API the order would have to flip.

A skip is a recorded event, not an absence. An absence is invisible; a decision can be audited. Same instinct as recording an explicit persona override rather than silently skipping the router.

05Orchestration

A persona is not a prompt

It bundles four things: instructions, a tool allowlist, a model, and a description the router reads. That bundle is the unit of specialisation — “psychologist”, “health coach”, “researcher” are each one PERSONA.md.

---
name: assistant
description: The default. Use for anything about this project…   # ← the router reads THIS
tools: [list_files, read_file, remember]                          # ← the allowlist
model: claude-haiku-4-5
---
You are a helpful assistant with read access to this project's files.

The description is a tool description in disguise: it says when to use this persona, not what it is, because that is the decision the router makes.

Threads — one chat, several conversations underneath

Each persona keeps its own transcript. Interrupting a coaching session to make a note and coming back works because the coach's thread was never touched.

The router is sticky by construction. Most turns continue what you were already doing, and a follow-up like “why would you pick that?” contains nothing naming coaching. A router without stickiness misfiles constantly; one with it only has to notice genuine changes of subject. It never fails a turn — on an API error, a truncated reply, or an unrecognised name it stays put and records why.

Delegation layer 8b

delegate becomes a tool, so a sub-agent is just another loop started from inside a loop. Two guardrails are already specified: a depth cap, and the subset rule — a child's allowlist must be a subset of its parent's. A child may never hold more privilege than its caller.

The allowlist is enforced once, at the gate

if isinstance(allowed, str) or name not in allowed:
    raise ValueError(f"{name} is not in this persona's allowlist")

Filtering the schemas the model sees is advisory — a model that saw a tool name earlier in the conversation can still emit it. So the check sits at dispatch, before any branch touches its arguments. The isinstance guard catches an allowlist flattened into one string, which would otherwise grant every tool whose name appears anywhere inside it.

07LLMOps: the outer loop

The inner loop answers your message. The outer loop improves the system that answers it. This is the half that makes it engineering rather than prompting — and it is the half that does not exist yet.

Trace — built layer 3

One row per turn. A turn is everything between your message and the reply, however many model and tool calls that took.

CREATE TABLE traces (
    id, started_at, duration_ms, user_input, reply,
    model_calls, input_tokens, output_tokens, cost_usd,
    events TEXT NOT NULL   -- JSON array, in the order they happened
);

events holds every decision — route, gate, model, tool — and that array is what makes a turn reconstructable afterwards. Cost is computed locally from a pricing table rather than reported by the API, so an unknown model shows as zero and is flagged unpriced, instead of silently claiming it was free.

08Self-improvement

The agent proposes a new skill, tool or agent; you approve; it designs; you approve the PR. The architecture splits that into two stages, and the split is the safety property.

Stage 1 layer 9 — the architect persona can write a proposal and nothing else. It holds no write tools. Its output is a structured document, not a change.

Stage 2 layers 13–15 — the guarded set is an allowlist over roots: everything under these paths is guarded, except these specific extension points. The system may add a new tool where an extension point allows it; it may not edit the code enforcing the boundary.

None of this is built. It is fully specified in ARCHITECTURE.md § Self-extension, which is the most carefully reasoned part of the design and worth reading in full.

The semantic row matches on the default, not on the whole design. Waku's default is FTS5 keyword search with no embedding, and so is this system's. But waku calls that “a boring default and a documented upgrade” — pgvector and three memory services plug in behind the same interface. The parked vector branch was the upgrade path, built before the base was finished.

The gate differs, and it matters more. Waku's gate is a small-model call that decides whether to retrieve and writes the search query; it fails open, retrieving anyway if the gate errors. This system's gate is a free keyword match that skips when nothing hits. Waku pays one small call per turn to get better queries.

The inner loop here is close to complete. The outer loop does not exist. That is where the next work belongs, and it maps exactly onto layers 10 and 11.

10The LangGraph question

Layer 12 is already “LangGraph port”, for a reason: build it by hand once, then port it. You cannot judge what a framework does for you until you have done it yourself.

Recommendation

Adopt LangSmith early. Adopt LangGraph late.

LangSmith replaces something you have not built — eval, judge, diagnose, release gate — and it is additive. You can point it at the current code without restructuring anything.

LangGraph replaces something you have built and understand. Porting now costs you the thing you are here to learn. Port at layer 12 as planned, once the hand-rolled version is feature-complete — then the diff is the lesson.

LangChain the base library: piecemeal or not at all. Its abstractions are the ones most likely to hide the mechanics you want to see.

11Evidence from the parked branch

A branch replacing FTS5 with local embeddings was built to five of six tasks, then parked. What it measured is worth keeping, because it explains why the keyword design is defensible rather than merely simpler.

Embeddings rank well. Top-1 correct 5/5 with a bi-encoder and 6/6 with a cross-encoder reranker — including cases FTS5 provably cannot reach, like “tell me about my testing background” matching a QA fact that shares no words with it.

Embeddings cannot gate. No cosine floor separates relevant from irrelevant queries, at any model size:

Modeldimlowest relevanthighest irrelevantseparation
bge-small-en-v1.53840.5120.651−0.139
bge-base-en-v1.57680.4640.543−0.079
gte-base7680.7490.776−0.027
mxbai-embed-large-v110240.4120.519−0.108

Never positive. Margin and z-score separate worse. Cross-encoders rank better and gate no better.

Ranking is cheap and solvable; judging relevance is not a similarity problem. Which is a good argument for cheap keyword retrieval plus an LLM judgement — and that is what waku's gate does: a small model decides whether to retrieve, keyword search does the retrieving.

A second finding, independent of backend. A fact-to-fact dedup threshold at 0.85 silently destroys distinct facts: “standup is at 9am” and “standup is at 10am” score 0.947. The only safe window measured was 0.947–0.981. If dedup is ever built, on any backend, it needs that calibration or it will quietly eat real data.
